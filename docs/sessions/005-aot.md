# Session 005 — AOT executables

**Date:** 2026-05-19
**Outcome:** `rune build examples/fib.rn` produces a 130KB native `fib.exe`
that exits with code 55. 8 new AOT integration tests; 129 total green.

## Goal

Take type-checked Rune source all the way to a standalone native
executable — no JIT runtime, no Rune compiler at runtime, just an
honest-to-goodness `.exe` you can run from anywhere.

## Three pre-decisions pinned

| Decision | Choice |
| --- | --- |
| Output format | Native executable (`.exe` on Windows, no extension elsewhere). Static library / DLL output deferred indefinitely. |
| Opt level for `rune build` | `none` by default (fast iteration). A `--release` flag mapping to Cranelift `speed` is the obvious follow-up but doesn't ship in this session. |
| Linker discovery | Try `$RUNE_LINKER` first, then `clang` → `gcc` → `cc`. The first that succeeds wins. |

LANGUAGE.md Compilation model expanded to cover both JIT and AOT modes
(both Decided).

## Architecture

```
AST ─▶ HIR ─▶ codegen.rs (generic over cranelift_module::Module)
                  │                        │
                  ▼                        ▼
           Codegen<JITModule>      Codegen<ObjectModule>
                  │                        │
                  ▼                        ▼
            in-memory code         object bytes → linker → .exe
            (rune run)             (rune build)
```

The big refactor in `codegen.rs` was making the existing `Codegen` struct
generic over the `Module` trait:

```rust
pub struct Codegen<M: Module> { module: M, ... }

impl<M: Module> Codegen<M> {
    pub fn compile_module(&mut self, hir: &HirModule) -> Result<...>;
    fn fn_signature(...);
    fn define_fn(...);
}

impl Codegen<JITModule> {
    pub fn new_jit() -> ...;
    pub fn finalize(&mut self) -> ...;
    pub fn get_function_ptr(&self, sym: SymbolId) -> ...;
}

impl Codegen<ObjectModule> {
    pub fn new_object(name: &str, opt: OptLevel) -> ...;
    pub fn emit_c_main_wrapper(&mut self, rune_main_id: FuncId) -> ...;
    pub fn finish(self) -> Result<Vec<u8>, ...>;
}
```

`FnCodegen` is similarly generic: `struct FnCodegen<'a, M: Module> { ... }`.
Every line of per-function codegen — `iadd`, `brif`, `def_var`, block-param
threading — is shared verbatim between JIT and AOT.

## The C main wrapper

Rune source declares `fn main() -> i64`. The OS expects an entry point named
`main` with C signature `int main(void)` (the CRT's `mainCRTStartup` on
Windows, `_start` on Linux, both call `main`).

Two collisions to resolve:
1. **Name**: both Rune's main and the C entry are called `main`.
2. **Signature**: Rune's `() -> i64` vs C's `() -> i32`.

`src/aot.rs::build_object` handles both before handing off to Cranelift:

```rust
fn rename_main(hir: &mut HirModule) -> Option<SymbolId> {
    for item in &mut hir.items {
        let HirItem::Fn(f) = item;
        if f.name == "main" {
            let sym = f.sym;
            f.name = "__rune_main".to_string();
            return Some(sym);
        }
    }
    None
}
```

Then after `compile_module`, we synthesize a fresh `main` in Cranelift IR:

```cranelift
function main() -> i32 {
block0:
    v0 = call __rune_main()
    v1 = ireduce.i32 v0
    return v1
}
```

`ireduce` is Cranelift's truncating int-cast — drops the high 32 bits of the
i64. Result becomes the process exit code.

## Linker discovery

`cranelift-object` produces a relocatable `.o`. To get an executable we need
a linker plus C runtime startup files (mainCRTStartup on Windows, crt1.o /
glibc on Linux). The easiest portable approach is to use a C compiler
*driver* — `clang foo.o -o foo.exe` — which knows where the CRT lives.

`src/aot.rs::link` tries linkers in order:

```rust
let candidates = if let Ok(custom) = env::var("RUNE_LINKER") {
    vec![custom]
} else {
    vec!["clang".into(), "gcc".into(), "cc".into()]
};
for cand in &candidates {
    let result = Command::new(cand).arg(obj).arg("-o").arg(output).output();
    if result.is_ok_and(|out| out.status.success()) { return Ok(cand.clone()); }
}
```

This works because all three drivers accept the same minimal invocation —
`<driver> <obj> -o <out>` — and handle CRT linking themselves. We never have
to know the path to libc or to set `/SUBSYSTEM:CONSOLE`.

On this machine the test platform is Windows 11 with MSYS2 UCRT64 clang and
gcc. Cranelift produces MSVC-style COFF (since rustup is configured for
`x86_64-pc-windows-msvc`); MSYS2 clang happily links it against ucrt and
produces a working ucrt-linked `.exe`. Cross-toolchain mismatch is invisible
because both ends speak the COFF object format and the user-side code makes
no libc calls.

## What goes in `.o` vs `.exe`

For `examples/fib.rn`:

| File | Size | Contents |
| --- | --- | --- |
| `fib.o` | 342 bytes | Cranelift's emit — just `fib`, `__rune_main`, `main` machine code + relocations |
| `fib.exe` | 130 KB | Above + clang's CRT startup, `mainCRTStartup`, exception unwinding tables, ucrtbase imports, PE/COFF headers |

The 380× size difference is essentially all C runtime. A future "freestanding"
target would emit a much leaner executable.

## Apparent bugs that aren't

- **`rune build foo.rn` requires a linker on PATH.** If none of `clang`,
  `gcc`, `cc` is installed, build fails with a clear "no working linker
  found" error listing what it tried. Not a Rune bug — it's intentional
  delegation to the host toolchain.
- **The intermediate `.o` is left next to the executable.** Deliberately —
  it's useful for `objdump`-style inspection. Future improvement: a
  `--keep-intermediate` flag with the default flipped to deletion.
- **`rune build` on a program without `main` fails late.** The check
  happens in `build_object`, after we've already lex/parse/check'd. The
  error message is clear (`no \`main\` function in module`) but a
  preflight check could surface it earlier.

## Test coverage

8 end-to-end tests in `tests/aot.rs`:
- Literal return (42)
- Zero exit
- Arithmetic (`1 + 2 * 3` → 7)
- Conditional (`if x > 5 { x * 2 }` → 20)
- While-loop accumulator (sum 1..=10 → 55)
- Recursive factorial (5! → 120)
- Recursive fib (fib(10) → 55)
- Cross-function calls (3 levels deep → 42)

Each test:
1. Compiles a Rune program to `.o` via `aot::build_object`.
2. Invokes `clang` (or fallback) to link to a temp `.exe`.
3. Runs the executable.
4. Asserts the exit code matches the expected `main()` return value.

Each runs in ~150ms — most of that is the linker invocation. Tests run in
parallel; unique temp paths via a global `AtomicUsize` counter avoid
collisions.
