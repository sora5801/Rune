# Session 089 — Cartesian-product exhaustiveness for tuple patterns

**Date:** 2026-05-25
**Outcome:** `match` on a tuple scrutinee with mixed-
position patterns now closes when the cartesian product
of per-position constructors is fully covered. Closes
session 082's deferred item. 411 codegen tests green
(+5 from session 088).

```rune
match (b, x): (bool, i64) {
    (true, x) => ...,        // closes "true" × all-i64
    (false, _) => ...,       // closes "false" × all-i64
}
// → exhaustive (was: error "add a `_` arm")

match (b1, b2): (bool, bool) {
    (true, _) => ...,
    (false, true) => ...,
}
// → still non-exhaustive — `(false, false)` falls through
//   (correctly diagnosed; flat per-position would've missed it)
```

## The decisive observation

The pre-089 exhaustiveness check ran a flat per-type
coverage set (bools, variants, ints, strs). Tuple
patterns treated "every sub-pattern is wildcard /
ident" as a catch-all and otherwise didn't contribute.
That under-reports both directions:

- False negatives: `(true, _)` + `(false, _)` should
  close `(bool, *)` but didn't.
- False positives: a naive per-position view would say
  `(true, _)` + `(false, true)` closes `(bool, bool)`
  (every position has both bool values somewhere). It
  doesn't: `(false, false)` is uncovered.

The general fix is Maranget's "usefulness" algorithm.
For a tuple scrutinee, it specializes the pattern
matrix one column at a time:

1. For the head column's type, enumerate its
   constructors (true / false for bool; every variant
   for enum; "default-only" for infinite types).
2. For each constructor c, build the specialized
   matrix: rows whose head pattern matches c, with the
   head column stripped.
3. Recurse on the tail tuple. Base case: 0 columns →
   exhaustive iff any row survived.

### Specialization rules

- **Wildcard / Ident in head**: matches any
  constructor; survives every specialization.
- **Specific literal / variant**: matches only its
  own constructor; survives just that specialization.
- **Default specialization** (for infinite-domain
  head types): keep only wildcard-headed rows.

The base case — `elem_tys.is_empty()` — says the
matrix is exhaustive iff at least one row survives.
An empty row matches the empty tuple `()` and any
caller can reach the base case only after every column
has had a constructor matching the row's head, so a
surviving empty row means there's a path through every
constructor to a matching arm.

### Or-pattern flattening

Top-level or-patterns expand row-wise: `(true, _) |
(false, _)` becomes two rows. Or-patterns nested
inside tuple sub-patterns aren't generated by v0.x
(the lowerer rejects or-in-tuple), so the matrix
algorithm doesn't need to handle them there.

### Bare `_` and ident arms still close

A bare `_` (or ident) arm for the whole tuple is a
catch-all — every sub-position becomes a wildcard
row. A pre-pass detects these (along with tuple
patterns whose every sub-pattern is recursively a
catch-all) and short-circuits as before. Subsequent
arms are flagged unreachable, same as the flat path.

## Apparent bugs that aren't / explicitly deferred

- **Nested tuple sub-patterns** — `match (a, (b, c))
  { ... }`. The matrix algorithm could recurse into
  nested tuples but doesn't yet: the head column's
  type would be Ty::Tuple, which falls into the
  "infinite / default-only" branch and requires a
  wildcard at that position to close. Workaround:
  flatten the tuple or write a wildcard at the
  nested position.
- **Range / int-lit patterns at tuple positions** —
  treated as "specific value" with no enumeration
  (i64 is infinite). Falls into default-only, so
  closes only via a wildcard. Same shape as the flat
  path: `match x { 0..=10 => ... }` alone isn't
  exhaustive on i64.
- **Payload-bearing enum variants** at tuple
  positions — `(Option<i64>, bool)` would need
  enumeration over Some(_) and None plus
  per-variant payload coverage. Current
  specialize_enum_disc treats every variant as a
  single constructor (ignoring payload), so
  `(Option::Some(_), _) | (Option::None, _)` closes,
  but `(Option::Some(5), _) | (Option::None, _)`
  doesn't (the Some-with-5 arm is specific, but
  variant disc still matches for Some — and the
  algorithm would think Some-with-any closes). The
  practical impact is "false positive exhaustive"
  for payload-specific tuple matches; users
  shouldn't depend on it.
- **Guards** — guarded arms contribute nothing to
  exhaustiveness (the guard can fail). Same shape as
  flat-path. An `if cond` arm doesn't close even if
  its pattern is a tuple catch-all.
- **Unreachable arms inside tuple matches** — the
  pre-pass detects "an unguarded catch-all arm
  followed by anything" via
  pattern_is_catchall_for_tuple, but a
  later-but-shadowed specific arm (`(true, _)`
  followed by `(true, true)`) isn't flagged. The
  matrix algorithm doesn't track per-arm
  reachability; getting that would require an
  additional pass (Maranget's "usefulness" test
  applied to each arm against the matrix of all
  earlier arms). Reserved for a future polish pass.
